# Rubric: is this plan ready to post and build from?

This rubric grades one plan package: a candidate plan and a candidate
plan comment, read against the issue, its thread, the repo's stated
conventions, and the reproduction evidence the plan builds on. Every
check judges the plan itself (is the cause the one the evidence shows,
is the change one bounded fix, could a stranger start on it, would the
test prove anything) and never the write-up's shape. A terse plan with
no headings can pass every check; a long, confident, well-formatted
plan can fail one.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diagnosis-grounded | The plan's stated cause (and the cause the plan comment asserts), read step by step against the repro evidence block: every control run, every contrast, and every step that says where the behavior appears or disappears. | Pass if no step or control in the repro evidence contradicts the stated cause, so that the change the plan makes is at the place the evidence points to. A cause need not explain every observation in full: a step the plan explains with a hypothesis it has not tested, or does not explain at all, is not a contradiction and does not fail this check. Fail only if a repro step or control rules the stated cause out: a control where the blamed component works correctly under the same conditions, a step showing the damage has already happened before the blamed code runs, or a step showing the behavior with the blamed component absent. Also fail if the plan dismisses a variable the evidence shows deciding the outcome (calling it a "red herring" or "side effect") without evidence of its own. Agreeing with the issue, the thread, or a confident commenter does not pass this check on its own: where the repro evidence and a stated diagnosis disagree, the repro evidence wins. | required |
| scope-bounded | The plan's list of changes, its in-scope and not-in-scope statements, and its files, read against the single behavior the issue reports and the repro reproduces; plus the plan comment's description of what will be built. | Pass if every change the plan commits to building is needed to fix the reproduced behavior or to test that fix. Small adjacent work is still in scope: the same fix applied at sibling sites of the same defect in the same function, checking that each tool or caller the fix touches still works, regression tests, and running an existing test corpus. Work the plan explicitly defers, files as a separate issue, or leaves to a follow-up does not count against it, and deferring is the passing shape. Fail if the plan commits to building, as part of this change, work the reported behavior does not need: a dependency upgrade or library migration, a rewrite or restructure of a module or subsystem, unifying behavior across other components or constructs, a new user-facing option, setting, or prop, a new retry or abstraction framework, a CI matrix, or a fix for a different symptom. A correct core fix does not rescue a plan that bundles such work with it. | required |
| executable | The plan's files or code areas, its approach, and its order of work. | Pass if a stranger who has read the package could start the change today without asking the author what to do: the plan names the file, function, or a specific code path where the change goes, and states one chosen mechanism for the change (what the code will do differently). One narrowly named unknown is allowed when the area and mechanism are already chosen, for example "the exact function inside the client attach path will be pinned while tracing" or "the clamp site may be one layer up". Fail if the plan names no file or code area, or leaves the deciding choices open: "somewhere", "not sure which layer", "upstream or vendored, whichever is easier", "profile and optimize whatever shows up", "investigate, then fix once the cause is clear", or a list of options to try without one chosen. | required |
| test-decisive | The plan's test plan, read against the repro evidence's steps and their recorded output. | Pass if the test plan re-runs the reproduced trigger (the repro's command, script, or steps, or an equivalent regression test built from them) and names the observable result that must appear after the fix: a specific output, value, exit status, rendered state, or log line that differs from what the repro recorded. Fail if success is stated only as a feeling or an absence of complaint ("should feel fast", "nothing else should feel broken", "should work correctly"), or if the only test is running the existing suite with no check of the reproduced behavior itself. | required |
| thread-aware | The plan comment and the plan, read against the thread highlights: any comment by a maintainer (OWNER, MEMBER, or COLLABORATOR) that names a culprit location, a fix direction, an approach already rejected, or a posted patch or test build; and any open pull request or patch for this issue named in the thread. | Pass if, for each such maintainer direction and each such open PR or patch, the plan comment either follows it or names it and says why the plan differs; acknowledging an open PR and stating how this work relates to it (not racing it, contributing tests to it, rebasing onto it) passes. Pass if the thread has no such direction and no open PR or patch. Fail if the plan goes in a different direction from a maintainer's stated culprit, fix direction, or posted patch, or reuses an approach a maintainer rejected, and the comment never mentions that direction. | required |
| repo-policy | The repo-facts block's stated contribution policy, including any AI policy, read as conditions on the plan comment being posted. | Pass if the plan comment meets every condition the policy places on comments. Where the policy requires that AI usage in any form be disclosed (not only in pull requests or code), the comment must disclose it, naming the tool or the fact of AI assistance and its extent; the packages graded here are AI-assisted work, so a comment that says nothing about AI is non-disclosure and fails. Where the policy requires comments to be in the contributor's own words, the comment must read as a person's specific account rather than generic filler. Where the policy places no condition on comments (no AI policy, a "you are responsible for what you submit" policy, a ban only on fully AI-generated contributions, or a disclosure duty scoped to pull requests or code), this check passes on that ground with no disclosure needed. | required |
| unknowns-stated | The plan's risks, unknowns, and open questions, and every certainty the plan comment asserts. | Pass if the plan either names at least one real risk or unknown of its own change, or makes no claim of certainty beyond what the repro evidence shows. This check never changes the verdict; it marks the difference between a plan that says what it has not verified and one that does not. | preferred |

## Verdict rule

The verdict is `accept` if and only if every `required` check is graded
`pass`. One `required` check graded `fail` makes the verdict `reject`.
A `required` check graded `unclear` counts as `fail` and makes the
verdict `reject`: a plan whose readiness I cannot verify from the
package is not ready to post, and the fix belongs to the author
supplying what is missing, not to the grader assuming it. Grade
`unclear` only when the evidence the check names is genuinely absent
from the package, never as a way to avoid deciding a close call; for a
close call, apply the pass condition's wording and choose pass or fail.

`preferred` checks never change the verdict in either direction. Report
their grades so the author sees what would strengthen the plan, then
set them aside when applying the rule above.
